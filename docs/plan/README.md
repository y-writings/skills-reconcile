# skills-reconcile 新ロードマップ

## 結論

`skills-reconcile` は、ローカル環境に分散している Agent Skill を見つけ、利用者が選んだ Skill を
自分のリポジトリへ取り込むためのツールとして作り直す。

最初の到達点は、`$HOME/.agents/skills` に存在する Skill の一覧を、ファイルを変更せずに表示すること
だけとする。TUI のフィルタリング、コピー先の構造、実際のコピーは、この一覧表示が完成した後に
別の判断として設計する。

## 製品の前提

- 解決したい問題は、各 Agent の配置先にある Skill がリポジトリへ収束せず、別のマシンへ同期されない
  ことである。
- 自作 Skill と第三者作成 Skill を製品上の管理区分にしない。
- `skills add` などで導入した第三者作成 Skill も、利用者が選べば fork のように自分のリポジトリへ
  コピーして管理できることを将来の前提とする。
- 取り込む Skill の選択、利用、改変、再配布、ライセンス確認は利用者の責任とする。
- ツールは作者や導入経路を推測して、取り込み可否を自動判定しない。
- 自作 Skill を素早く探すための UX は、複数の既知ディレクトリを一覧化し、TUI で絞り込むことで
  実現する。ただし、この UX は最初の実装には含めない。

## 今回破棄するもの

以前の `docs/plan/**` にあった移行計画、PR ID、manifest、remote/workspace の所有権区分、receipt、
`doctor`、`plan`、`apply`、`prune`、`adopt`、v1 互換計画は、すべて今後の実装根拠から外す。

既存のソースコード、テスト、Nix、コンテナ、固定済み外部 CLI は、現在の挙動を確認するためには
参照できるが、新しい製品仕様の根拠にはしない。新ロードマップに必要ないものは、ビルド可能な状態を
保ちながら段階的に削除または置換する。

## 最初のマイルストーン

最初に実装する利用者価値は次の一文に限定する。

> 利用者は `$HOME/.agents/skills` にある Skill の一覧を読み取り専用で確認できる。

このマイルストーンでは、次を行わない。

- `.claude`、`.codex`、`.opencode` など、他の配置先の走査
- TUI の起動、検索、フィルタリング、複数選択
- Skill のコピー、移動、削除、編集
- コピー先リポジトリの構造決定
- 自作・第三者作成・導入経路・ライセンスの分類
- manifest、lock、receipt、外部 `skills` CLI の読み取り
- 複数マシンへの配布または同期

## 実装の順序

1. 一覧表示の完全な CLI 契約を文書で決める。
2. 合成した `.agents/skills` fixture に対して、Skill を読み取り専用で発見するコアを作る。
3. 承認済み契約どおりに一覧を表示する CLI を公開する。
4. 旧方針だけに必要だったコードと依存関係を除去し、Go、Nix、コンテナの経路を新しい最小製品へ
   そろえる。
5. 一覧表示が安定してから、走査対象ディレクトリ、TUI、コピー先構造の順に契約を決める。

詳細な PR 境界は [PR ロードマップ](pr-roadmap.md)に記載する。

## 計画の変更方法

各段階では、一つの利用者向け振る舞いと対応テストを同じ変更に含める。未決の後続機能を先回りして
抽象化しない。TUI やコピーの設計判断が必要になった時点で、実装より先にこの計画と CLI 契約を更新する。
