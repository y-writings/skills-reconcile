# PR ロードマップ

## リセット宣言

旧ロードマップの P、C、J、R、M、A、D、W、K、T、L、F で始まるすべての項目は廃止する。
完了済みか未完了かにかかわらず、新しい作業の依存関係や実装根拠にはしない。

新しい ID は `N` から始める。

## 進め方

- 一つの PR は、一つの利用者向け振る舞いまたは一つの明確な基盤整理だけを扱う。
- 利用者向け interface は、CLI 契約を文書で先に承認する。
- 実装と、その振る舞いを固定するテストを同じ PR に含める。
- regular feature PR は最新の成功した `main` から開始する。stack は明示的に依頼された場合だけ使う。
- 手書きによる非テスト実装の追加行と削除行は 500 行以下にする。
- 実装、テスト、fixture の手書き総差分が 1,000 行を超える場合は、責務が複数ないか確認して止める。
- 旧実装を温存するための互換 layer は作らない。
- TUI やコピーを想定した抽象化を、一覧表示の段階で追加しない。

## フェーズ 1: `.agents/skills` の一覧表示

| ID  | 責務                                           | 主な成果物                                    | 完了条件                                                                              |
| --- | ---------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------- |
| N01 | 一覧表示の CLI 契約を承認する                  | `docs/plan/cli-contract.md`                   | 実装に必要な Skill 認識条件、symlink、異常系、出力、終了 status、副作用が確定している |
| N02 | Skill discovery core を新規実装する            | 最小 package、合成 fixture、unit test         | 一時 `.agents/skills` から契約どおりに Skill を列挙し、何も書き込まない               |
| N03 | 一覧 CLI を公開する                            | entrypoint、black-box test                    | N01 の契約に一致する                                                                  |
| N04 | 旧方針のコードと runtime dependency を除去する | 不要 package・Node dependency・wrapper の整理 | 一覧表示に不要な旧 domain code がなく、Go build と test が成功する                    |
| N05 | 配布経路を新しい最小製品へそろえる             | Nix、コンテナ、CI、利用文書                   | Go、Nix、コンテナから同じ読み取り専用 CLI を実行できる                                |

N04 は N02 や N03 に必要な旧コードまで先に削除しない。各 PR の終了時点で、現在公開済みの機能を
build・test できる状態を維持する。生成済み lockfile の大きさではなく、手書き責務で PR を分ける。

## フェーズ 2: 走査対象と TUI

このフェーズは一覧表示の完了後に計画を具体化する。現時点では次の判断順だけを固定し、command 名、
設定形式、TUI framework、key binding、フィルター構文は決めない。

1. `.claude`、`.codex`、`.opencode`、`.agents` など、走査対象と優先順位を決める。
2. 同名 Skill を複数の配置先で見つけた場合の表示方法を決める。
3. TUI の一覧、フィルタリング、選択に関する UX 契約を決める。
4. 読み取り専用の TUI を実装する。

## フェーズ 3: リポジトリへの取り込み

このフェーズも未設計とする。実装前に、少なくとも次を別の文書変更で決める。

- コピー先リポジトリの directory layout
- Skill 名と destination path の対応
- 同名、同内容、変更済み、symlink、特殊ファイルの扱い
- 上書きしない既定動作と、再実行時の挙動
- 部分失敗を残さない書き込み方法
- 取り込み前に利用者へ示す source path と注意事項

作者区分や `skills add` の provenance は、コピー可否の自動判定には使用しない。

## フェーズ 4: 複数マシンへの反映

取り込み機能が完成した後に、Git で管理した Skill を別マシンと各 Agent の配置先へどう反映するかを
設計する。symlink、copy、外部 installer のどれを採用するかは現時点で決めない。

## 各 PR の共通チェックリスト

- [ ] この PR の責務を一文で説明できる。
- [ ] 利用者向け interface には、先に承認された CLI 契約がある。
- [ ] 未決の後続機能を推測して実装していない。
- [ ] 自作・第三者作成を自動分類していない。
- [ ] 実 HOME や実 Skill をテスト入力にしていない。
- [ ] 読み取り段階ではファイルを変更していない。
- [ ] 実装と対応テストを同じ PR に含めている。
- [ ] 手書き非テスト実装が 500 行以下である。
- [ ] Go format、unit test、対象 smoke test が成功している。
- [ ] 旧ロードマップの用語や挙動を新しい契約へ暗黙に持ち込んでいない。
